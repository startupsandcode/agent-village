# Design-led bounded missions

This milestone can start one design-led mission in `startupsandcode/agent-village` from a clean named feature branch. It asks Maya to return an agreed scope, summary, and testable criteria. The CLI presents that proposal and requires one exact user acceptance before it creates the durable mission. If Maya flags an unresolved scope, access, budget, or destructive-action question, the CLI stops before creating a mission.

After that single agreement, the CLI stores the accepted mission and launches one detached local worker. Stage adapters call the installed Codex CLI in this order:

1. Susie returns a structured guide with concept, hierarchy, typography, spacing, responsive states, imagery and interactions.
2. Sam receives that persisted guide and the agreed acceptance criteria. His CLI run uses the workspace-write sandbox with automatic approval review; it cannot publish, merge, provision resources, or add credentials.
3. Quinn receives the agreed criteria and Sam's preview candidate in a read-only run.
4. Playwright opens the exact approved URL in Chromium, blocks requests to other origins, checks the rendered artifact marker, title, heading, fonts, image alt attributes and horizontal overflow at desktop and narrow sizes, and captures screenshots.
5. Susie receives both real screenshots in a read-only visual-review run. A bounded revision returns to Sam, then repeats Quinn and Susie review.

The append-only journal stores Maya's accepted scope, design-guide data, stage outputs, attempts, review feedback, browser evidence and final state. A single-use local lock rejects duplicate runs. The dispatcher serializes mission intake and permits only one nonterminal mission in this shared workspace; a second start is refused before Maya is called. This avoids concurrent agents writing to the same checkout. Cancellation is checked at stage boundaries. The CLI caps each stage at two attempts, the visual revision loop at one, and each mission ID at eight total Codex CLI calls across Maya's pre-agreement clarification/proposal calls and all accepted-mission stages. A durable per-ID intake counter reserves the call before Maya is invoked; failed calls and clarifications consume the same allowance, and input files cannot raise it. If all eight are consumed before agreement, the mission ID is stopped and cannot launch worker stages. Durable attempt counters conservatively consume the role-call allowance before role launch, so crash/retry cannot reset it. Retryable errors may resume only within the attempt and global call limits; uncertain writes and stale locks fail closed for manual reconciliation.

## Start a mission

Install the project browser dependency with `npm ci --prefix village` and install the matching Chromium binary with `npm exec --prefix village -- playwright install chromium`. Create a JSON input file containing a unique mission `id`, `goal`, an already-authorized `destination` URL, `artifactId`, and any additional `constraints`. Do not include secrets. Start the existing local preview server for that destination before the worker begins. The preview HTML must contain `<meta name="village-artifact-id" content="YOUR_ARTIFACT_ID">` so the browser can bind its screenshots to the requested artifact.

Set `VILLAGE_MISSION_WORKSPACE` to the root of a clean `startupsandcode/agent-village` checkout on a named feature branch. The CLI adds fixed no-production, no-paid-resources, no-new-credentials, and ownership constraints. It caps each mission ID at eight Codex CLI calls total, including Maya clarification/proposal calls before acceptance and stage retries afterward. Then run:

```powershell
node village/mission-cli.mjs start .\mission-input.json
```

The default durable state and evidence directories are `~/.agent-village/missions` and `~/.agent-village/evidence`; override them with `VILLAGE_MISSION_ROOT` and `VILLAGE_MISSION_EVIDENCE_ROOT`. Completion events are written to `missions/.notifications/`; override that path with `VILLAGE_MISSION_NOTIFICATIONS_ROOT`. The `start` command returns after it launches the detached worker, so the terminal and browser can close while the mission continues. The worker is a normal user-session process: it runs only while the machine and user session remain available. It does not install a service, register at startup, or restart after reboot.

Use `node village/mission-cli.mjs status <id>` to inspect the durable manifest, worker PID, latest worker error, and completion events. `node village/mission-cli.mjs notifications` reads the local completion feed; `show`, `cancel`, and `resume` remain available. The local Office page now renders running, accepted-preview, cancelled, and error/attention states from the same local mission store, with a link to a verified preview and keyboard-accessible refresh. It identifies itself as local-only; hosted Office cannot see desktop files. The manifest pins the original feature branch. Resume requires that branch and a clean checkout; a dirty or changed branch stops for reconciliation. When a worker exits unexpectedly, `status` reports whether its PID remains alive and `notifications` records the worker error. An in-flight role stage or stale lock remains blocked for manual reconciliation because its write outcome may be uncertain. Accepted missions are durable as `ready` manifests; there is no general multi-item queue because this first slice shares one checkout.

## Verification boundary

The test suite includes real Chromium against an ephemeral local HTTP preview and a full CLI integration test with mock role outputs. It verifies that the browser, exact destination, artifact marker, screenshots, screenshot digests and desktop/narrow states work together. Unit tests also exercise role order, Maya agreement, guide enforcement, failure/retry, cancellation, duplicate execution, queued-job serialization, worker credential filtering, completion events and uncertain-write handling. The Codex role adapter uses the real CLI contract, schemas and permissions, but this task did not launch a live role: a live `codex exec` can consume the account's existing Codex quota, and no paid agent run was authorized.

This worker does not deploy or publish. Sam must return a URL that already serves the accepted artifact at the exact approved destination; otherwise browser review blocks. The local Office server exposes a read-only `GET /api/missions` projection from the same user-scoped mission store; it returns mission status, timestamps, attention state, and a preview URL for verified completion without exposing stage prompts, design guides or evidence paths. The local Office UI renders that projection, but hosted Office cannot read the desktop user's local mission files. Connecting hosted Office requires a deliberate authenticated owner-scoped shared store/event bridge and is not configured here. The durable completion feed does not yet send an OS notification, email, or message to the user. There is no unattended scheduler or restart-on-boot hook. If the machine sleeps, the user session ends, or the process crashes, execution stops; crash recovery does not replay an uncertain stage automatically.

The role adapter requires `codex login status` to identify a ChatGPT session and removes `OPENAI_API_KEY` and `CODEX_API_KEY` from the child process environment, so it does not intentionally fall back to API-key billing. This does not itself guarantee that work stops at included subscription usage: ChatGPT-authenticated Codex may use purchased/flexible credits when enabled, and account settings can allow automatic reloading. The implementation has a hard eight-call ceiling for an accepted mission, but no dollar-denominated per-mission cap. A true no-overage live run requires the account owner to disable additional-credit/auto-reload use or set an applicable zero-overage workspace control before authorizing execution; even zero-overage controls may allow in-flight work to settle after the threshold.

## Future portfolio manager

The per-mission manifest and handler configuration are isolated so a later portfolio manager can coordinate multiple teams. That layer still needs project lists and priorities, one team/workspace per project, dependency coordination, shared budget and concurrency limits, and collision handling for repositories, branches, artifacts and preview destinations. This milestone starts only one mission and does not add those shared services.
