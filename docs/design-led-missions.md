# Design-led bounded missions

This milestone can start one design-led mission in `startupsandcode/agent-village` from a clean named feature branch. It asks Maya to return an agreed scope, summary, and testable criteria. The CLI presents that proposal and requires one exact user acceptance before it creates the durable mission. If Maya flags an unresolved scope, access, budget, or destructive-action question, the CLI stops before creating a mission.

After that single agreement, the CLI stores the accepted mission and launches one detached local worker. Stage adapters call the installed Codex CLI in this order:

1. Susie returns a structured guide with concept, hierarchy, typography, spacing, responsive states, imagery and interactions.
2. Sam receives that persisted guide and the agreed acceptance criteria. His CLI run uses the workspace-write sandbox with automatic approval review; it cannot publish, merge, provision resources, or add credentials. For a Vercel target, Sam must return a relative path to a complete static output directory instead of deploying it.
3. The runtime submits that output using the bounded Vercel Build Output API adapter. Maya's agreement binds the exact project and team IDs, preview environment, and generated-host pattern. The returned deployment ID, URL, and artifact fingerprint are checkpointed before Quinn runs.
4. Quinn receives the agreed criteria and the exact returned preview URL in a read-only run.
5. Playwright opens the exact returned URL in Chromium, blocks requests to other origins, checks the rendered artifact marker, title, heading, fonts, image alt attributes and horizontal overflow at desktop and narrow sizes, and captures screenshots. For protected Vercel previews, the browser attaches a short-lived development OIDC token only to that approved origin.
6. Susie receives both real screenshots in a read-only visual-review run. One bounded revision returns to Sam, then creates a revision-specific preview and repeats Quinn and Susie review.

The append-only journal stores Maya's accepted scope, design-guide data, stage outputs, attempts, review feedback, browser evidence and final state. A single-use local lock rejects duplicate runs. The dispatcher serializes mission intake and permits only one nonterminal mission in this shared workspace; a second start is refused before Maya is called. This avoids concurrent agents writing to the same checkout. Cancellation is checked at stage boundaries. The CLI caps each stage at two attempts, the visual revision loop at one, and each mission ID at eight total Codex CLI calls across Maya's pre-agreement clarification/proposal calls and all accepted-mission stages. A durable per-ID intake counter reserves the call before Maya is invoked; failed calls and clarifications consume the same allowance, and input files cannot raise it. If all eight are consumed before agreement, the mission ID is stopped and cannot launch worker stages. Durable attempt counters conservatively consume the role-call allowance before role launch, so crash/retry cannot reset it. Retryable errors may resume only within the attempt and global call limits. The exceptional `retry-preflight` command grants one additional Susie design attempt only when a local Codex session log proves the exact strict-schema HTTP 400 was rejected before assistant/tool output, the accepted mission and workspace match, and the previous worker is confirmed stopped. It preserves the failed attempt and counts the extra call toward the eight-call cap. Other failures and uncertain outcomes remain blocked for reconciliation.

## Start a mission

Install the project browser dependency with `npm ci --prefix village` and install the matching Chromium binary with `npm exec --prefix village -- playwright install chromium`. For an existing local preview, create a JSON input with a unique mission `id`, `goal`, exact approved `destination` URL, `artifactId`, and any additional `constraints`; start the preview server first. For Vercel, set `VILLAGE_VERCEL_PREVIEW_TARGETS` in the current shell to an explicit JSON allowlist of project/team IDs and slugs with `environment: "preview"`, then put that exact `previewTarget` object in the mission JSON instead of `destination`. Do not put credentials or secrets in the allowlist or mission file. Sam's static output must have root `index.html` containing `<meta name="village-artifact-id" content="YOUR_ARTIFACT_ID">`.

Set `VILLAGE_MISSION_WORKSPACE` to the root of a clean `startupsandcode/agent-village` checkout on a named feature branch. The CLI adds fixed no-production, no-paid-resources, no-new-credentials, and ownership constraints. It caps each mission ID at eight Codex CLI calls total, including Maya clarification/proposal calls before acceptance and stage retries afterward. Then run:

```powershell
node village/mission-cli.mjs start .\mission-input.json
```

The default durable state and evidence directories are `~/.agent-village/missions` and `~/.agent-village/evidence`; override them with `VILLAGE_MISSION_ROOT` and `VILLAGE_MISSION_EVIDENCE_ROOT`. Completion events are written to `missions/.notifications/`; override that path with `VILLAGE_MISSION_NOTIFICATIONS_ROOT`. The `start` command returns after it launches the detached worker, so the terminal and browser can close while the mission continues. The worker is a normal user-session process: it runs only while the machine and user session remain available. It does not install a service, register at startup, or restart after reboot.

Use `node village/mission-cli.mjs status <id>` to inspect the durable manifest, worker PID, latest worker error, and completion events. `node village/mission-cli.mjs notifications` reads the local completion feed; `show`, `cancel`, and `resume` remain available. For the verified Susie schema-rejection case only, `node village/mission-cli.mjs retry-preflight <id> <Codex-session-log>` verifies the transcript and reserves one audited retry; then `resume` launches the same mission. The local Office page now renders running, accepted-preview, cancelled, and error/attention states from the same local mission store, with a link to a verified preview and keyboard-accessible refresh. It identifies itself as local-only; hosted Office cannot see desktop files. The manifest pins the original feature branch. Resume requires that branch and a clean checkout; a dirty or changed branch stops for reconciliation. When a worker exits unexpectedly, `status` reports whether its PID remains alive and `notifications` records the worker error. Other in-flight role stages or stale locks remain blocked for manual reconciliation because their write outcome may be uncertain. Accepted missions are durable as `ready` manifests; there is no general multi-item queue because this first slice shares one checkout.

## Verification boundary

The test suite includes real Chromium against an ephemeral local HTTP preview and a full CLI integration test with mock role outputs. It verifies that the browser, exact destination, artifact marker, screenshots, screenshot digests and desktop/narrow states work together. Unit tests also exercise role order, Maya agreement, guide enforcement, failure/retry, cancellation, duplicate execution, queued-job serialization, worker credential filtering, completion events, uncertain-write handling, and evidence-bound pre-execution recovery. One authorized live mission was started: Maya proposed a bounded mission and John accepted it; Codex rejected Susie's first stage with HTTP 400 `invalid_json_schema` because the response schema omitted `artifactPath` from `required`. The request was rejected before assistant output or tool execution, no deployment was submitted, and the durable ledger reserves two of eight calls. The schema is fixed; the operator recovery command retains the failed event and allows one retry against the same mission identity.

The runtime now wires the adapter after Sam's implementation and before Quinn's review. It stages only static files under Vercel Build Output API `static/`, adds a version 3 output config, excludes credential/config paths and symlinks, requires the exact artifact marker, fingerprints the staged files, and calls `vercel deploy --prebuilt --target preview`. It does not run a Vercel build or create serverless functions. The response is checked against the accepted project, team, target environment, host pattern, deployment ID, mission ID, artifact ID and fingerprint before the URL is passed to Quinn and Playwright. Separate write-ahead journals bind each of the two allowed revision numbers; duplicate identical submissions reuse their ready result, while uncertain submissions stop for reconciliation. See [Vercel Build Output API static files](https://vercel.com/docs/build-output-api/primitives) and [Vercel CLI deploy](https://vercel.com/docs/cli/deploy).

Vercel deployment is opt-in per mission: the target must be present in both Maya's accepted agreement and `VILLAGE_VERCEL_PREVIEW_TARGETS`. If that allowlist is missing or mismatched, the mission is rejected before Maya is called. The official CLI's read-only `whoami` and `vercel env run` use the existing local Vercel login. For browser review, `vercel env run` supplies a short-lived development `VERCEL_OIDC_TOKEN` in memory; the verifier sends it as `x-vercel-trusted-oidc-idp-token` only to the approved preview origin and never writes or logs the token. Vercel's supported [protected-deployment skill](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/trusted-sources) says same-project development-to-preview self-access works by default. No protection setting, bypass, credential, or persistent grant is changed. If the CLI cannot provide its existing token or Vercel rejects the same-project access, visual review blocks without weakening SSO.

The adapter caps each static artifact at 1,000 files and 50 MiB, limits each browser review to 16 same-origin requests, waits at most 15 minutes for a ready deployment, and allows only one visual revision (two previews maximum). Using the official Vercel list rates as a conservative estimate, charging all 32 maximum browser responses at 50 MiB each for both CDN transfer ($0.15/GB) and origin transfer ($0.06/GB), charging both 50 MiB uploads at those rates, 32 CDN requests at $2 per million, and one month of storage for both outputs at $0.10/GB-month totals about $0.36. This intentionally charges origin transfer even though the output contains no functions or compute. [Static output deployments are not counted as builds](https://vercel.com/docs/limits); [Vercel pricing](https://vercel.com/docs/pricing) and [deployment storage rates](https://vercel.com/docs/deployment-storage) provide the inputs. The existing Astra Lab project API currently reports a 30-day deployment expiration and 10 deployments to keep. At the maximum artifact size, retained output is about $0.0098 per month after that period if an exception keeps it; this estimate stays below $1 for a single test for more than eight years at current rates, but Vercel does not provide a hard per-preview spend cap. Spend Management can lag and its automated pause does not cap a single preview. No deployment has been submitted by this code path.

The local Office server exposes a read-only `GET /api/missions` projection from the same user-scoped mission store; it returns mission status, timestamps, attention state, and a preview URL for verified completion without exposing stage prompts, design guides or evidence paths. The local Office UI renders that projection, but hosted Office cannot read the desktop user's local mission files. Connecting hosted Office requires a deliberate authenticated owner-scoped shared store/event bridge and is not configured here. The durable completion feed does not yet send an OS notification, email, or message to the user. There is no unattended scheduler or restart-on-boot hook. If the machine sleeps, the user session ends, or the process crashes, execution stops; crash recovery does not replay an uncertain stage automatically.

The role adapter requires `codex login status` to identify a ChatGPT session and removes `OPENAI_API_KEY` and `CODEX_API_KEY` from the child process environment, so it does not intentionally fall back to API-key billing. This does not itself guarantee that work stops at included subscription usage: ChatGPT-authenticated Codex may use purchased/flexible credits when enabled, and account settings can allow automatic reloading. The implementation has a hard eight-call ceiling for an accepted mission, but no dollar-denominated per-mission cap. A true no-overage live run requires the account owner to disable additional-credit/auto-reload use or set an applicable zero-overage workspace control before authorizing execution; even zero-overage controls may allow in-flight work to settle after the threshold.

## Future portfolio manager

The per-mission manifest and handler configuration are isolated so a later portfolio manager can coordinate multiple teams. That layer still needs project lists and priorities, one team/workspace per project, dependency coordination, shared budget and concurrency limits, and collision handling for repositories, branches, artifacts and preview destinations. This milestone starts only one mission and does not add those shared services.
